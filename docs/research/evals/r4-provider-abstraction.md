# R4 — Provider abstraction for the steering-effectiveness eval

Question: what is the one seam that lets a shell-driven Host harness (Claude Code `claude -p`, Antigravity `agy`) and a bare LLM endpoint (OpenAI-compatible or Anthropic Messages, configured in `.env`) both run the same case and return the same record, and what can each honestly measure?

This is design-as-research, not code. Terms follow `CONTEXT.md`. Three are not in it and are named here provisionally: **provider** (anything that can run one session), **stand-in host** (the minimal tool loop a bare-endpoint provider would need to write files), **delivery channel** (where the `mh` answer enters the model's context). They belong under "Glossary gaps".

Read before this: issue #222 (the eval suite spec; its decision 10 names exactly two impure seams, `runContributorSession` and `judge`), `docs/vision/architecture.md` tenets 1–3 and the Boundaries table, ARCH-003, ARCH-006, ARCH-007. Issue #222 has no comments.

## 1. Constraints the seam must respect

1. **Tenet 3 and the "Run a model or hold an API key" boundary** (`docs/vision/architecture.md` Boundaries row; `docs/vision/product.md` Boundaries). The product runs no model and holds no key. #222 decision 16 resolves this for the Host harness path: the repository's tooling asks the Operator's Host harness, on the Operator's own auth. A bare-endpoint provider is different in kind: the _repository's tooling_ would read a key from `.env` and call a network service itself. That does not breach the product boundary if the code never ships (the eval Package is not in the npm tarball and the key never reaches `mh`), but it is a stretch of the sentence in #222 decision 16 and of user story 13 ("the product holds no key and runs no model itself"). Spec agents must say so in the spec rather than discover it in review. See "What the spec agents must decide", item 1.
2. **Nothing with a model, key or network enters `npm run verify` or `ci.yml`.** Verification trap 13: a gate appended to `verify` never runs on a PR because `ci.yml` duplicates the chain, so the inverse is also true — a live script wired nowhere near either is safe, and an accident must be made structurally impossible, not merely unlikely. Section 6 lists the guards.
3. **ARCH-003: impure spawn seams unmocked and untested; everything above them pure and unit-tested with hand-written stand-ins, explicit inputs, no mocks, no snapshots.** The endpoint provider adds a second kind of impure seam (network, plus file writes), and the same rule applies: it is not tested, so the less code in it the better.
4. **ARCH-007: impure–pure–impure sandwich; a conditional must not encode a business rule.** Every decision (what argv to build, whether a reply is a tool call, whether a rung is measurable, whether a failure is instrument or graded) sits in a `.pure` file that takes its data as arguments.
5. **ARCH-006: a `.pure` file may not reach a platform builtin.** This bites twice. `util.parseEnv` and `fetch` are builtins, so `.env` parsing either lives in an impure file or is a hand-written pure parser over a string. Per tenet 7 (build when a defect would be loud) a 30-line parser is buildable, and a mis-parse fails loud as a missing key.
6. **Existing seams.** There is no production spawn seam in `src/`. `grep` finds `child_process` only in tests (`cli/tests/assess-hook.test.ts`, `cli/tests/query-hook.test.ts`, `cli/tests/cli.test.ts`, the `conformance/tests/*-tier.test.ts` runners) and in the `.agents/skills/markdown-harness/scripts/*.mjs` hooks, which sit outside `src/` and outside eslint and knip. The reusable precedent is the _process boundary itself_: the compiled `dist/` `mh`, spawned with a built root, which the Conformance runners already use and which #222 reuses for expectation checks. The two provider seams are new. They are not a reason to widen any existing file; the eval Package owns them.

## 2. The interface

One provider function, one request type, one record type. The framework never branches on provider kind; it branches on the record's declared capabilities.

```
runSession(request: SessionRequest, provider: ProviderSpec): Promise<SessionRecord>
```

### 2.1 SessionRequest (all fields explicit; nothing ambient)

| field           | meaning                                                                                                                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `root`          | Absolute path of the minted throwaway root: config, `AGENTS.md`, seed overlay, hook wiring when the provider supports hooks. The provider writes only inside it. Minting is pure planning plus one impure write, upstream of the provider.                                           |
| `task`          | The Contributor-voiced task text, verbatim, with no config text in it (#222 transcription guard).                                                                                                                                                                                    |
| `arm`           | `as-written` or `intent-neutralised`. The provider never inspects it: the arm is already baked into the minted `root`. It is carried through only so the record is self-describing. A provider that branches on the arm is a defect.                                                 |
| `caps`          | `{ maxTurns, maxOutputTokens, wallClockMs, maxToolCalls }`. A provider that cannot enforce a cap natively enforces it in its own loop and records which caps were native versus emulated.                                                                                            |
| `delivery`      | Which delivery channel carries the `mh` answer. For a Host harness provider the only legal value is `native` (the wired hook decides). For an endpoint provider it is `none`, `system`, `user-prefix` or `tool-result` (section 5). It is a cohort field, never an implicit default. |
| `trial`, `seed` | Trial index and a sampling seed where the provider honours one; recorded as honoured or not.                                                                                                                                                                                         |

The task text, the root and the caps are the only things the model's side sees. `delivery` selects among provider-internal behaviours and must change nothing for a `native` provider.

### 2.2 SessionRecord (what comes back)

1. **Outcome.** `outcome: 'ran' | 'instrument-failed'`. When `instrument-failed`, a `failure` carrying `kind` (`unconfigured`, `binary-missing`, `auth-rejected`, `network`, `rate-limited-exhausted`, `timeout`, `no-parseable-output`, `provider-refused-to-start`) and a redacted human message. `ran` means the provider produced a session the grader may score, including a session that did nothing. This is #222 decision 13 and user story 17 carried into the provider: a session where the agent wrote no file is a graded zero, and a session that never started is not a score at all.
2. **Produced tree.** The provider returns no file contents. It leaves `root` mutated and returns `changed: Array<{path, before: digest|null, after: digest|null}>`. A pure diff over two digest maps (impure walk before and after, pure compare) is the same code whatever the provider. The grader then reads files from `root` exactly as it would after a Host harness session. Both provider kinds therefore feed one grader.
3. **Normalised transcript events.** An ordered list. Every event carries `seq`, `kind` and `provenance`:
   - `kind`: `prompt`, `assistant-text`, `tool-call`, `tool-result`, `hook-output`, `file-write`, `mh-call`, `usage`, `error`.
   - `provenance`: `observed` (the provider saw it happen) or `simulated` (the provider's own stand-in did it).
   - A provider that cannot observe an event class emits none of that class. It never emits an empty placeholder, because absence is how the rung classifier knows a rung is _unobservable_ rather than _clean_.
4. **Capabilities actually exercised.** `{ hooksRan, toolsOffered, agentsMdDiscovered, mhCalledByAgent, transcriptComplete }`, each `true`, `false` or `unknown`, with `unknown` never coerced. `hooksRan` and `agentsMdDiscovered` are proved by a canary, not by configuration (section 4.1).
5. **Cohort metadata.** Extends #222's cohort row (agent model, judge model, Host harness version, `mh` commit, config digest, arm, trial, start instant, duration, turn count) with: `providerKind` (`host-harness` or `endpoint`), `providerId`, `wireFormat` (`claude-code-stream`, `agy-…`, `openai-chat`, `anthropic-messages`), `endpointHost` (hostname only), `delivery`, `mode` (`single-shot` or `stand-in-host`), `toolsOffered`, `temperature`, `capsNative` versus `capsEmulated`, and `modelSelfReported` versus `modelConfigured` when they differ. Two rows differing in `providerKind`, `delivery` or `mode` are never pooled.

### 2.3 What is pure and what is impure

Everything is `.pure` except the following impure files, each carrying one ambient dependency and nothing else (ARCH-007 section 1). Names are illustrative; ARCH-004 governs the real ones.

| impure file (one spawn or one network or one fs edge) | what it does and nothing more                                                                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `host-session.impure.ts`                              | Spawns the configured Host harness binary with a pure-built argv, a scrubbed env and a timeout; collects stdout, stderr, exit code and signal; returns them raw.    |
| `endpoint-transport.impure.ts`                        | One `fetch` of a pure-built request with the auth header added at the last moment; returns status, headers and body text.                                           |
| `stand-in-host-fs.impure.ts`                          | Applies one pure-planned write, read or list inside `root`, refusing any path that resolves outside it (tenet 3's own rule about targets outside the root, reused). |
| `env-file.impure.ts`                                  | Reads `.env` text and `process.env` into plain records.                                                                                                             |
| `tree-digest.impure.ts`                               | Walks `root`, returns a path-to-digest map.                                                                                                                         |

Pure and unit-tested with explicit inputs: argv builders per Host harness; the Claude Code stream-JSON parser and any `agy` output parser into normalised events; the `.env` parser; the endpoint request builder per wire format; the endpoint reply parser per wire format (text, tool calls, usage, errors); the stand-in tool-loop step function (`state`, `reply` to `next action`); the tool-call validator and path guard; the redactor; the failure classifier (raw exit, status, signal, stderr to `instrument-failed` kind or `ran`); the digest differ; the capability-to-rung coverage table (section 5); the cohort row builder; the delivery-channel assembler that decides where the `mh` JSON goes in a prompt.

The **spawn boundary** sits exactly at `host-session.impure.ts` and `endpoint-transport.impure.ts`. The loop that drives repeated model turns for the stand-in host is _impure orchestration over pure steps_: it calls transport, calls the pure step function, applies the planned action through the fs file, and repeats. It has no decisions in it; the step function returns `{ done }` or `{ do, next-request }`. This keeps the loop under ARCH-007's "sequence, do not decide".

The honest cost: the endpoint reply parsers are tested against **hand-written** fixture strings (ARCH-003 forbids mocks and snapshots), so they prove the parser against the author's belief about the wire shape, not against the real service. Drift between the two is a silent failure mode of exactly the kind trap 4 and trap 15 describe. Mitigation, not a test: the live half's first request per provider per run checks that the parsed reply has the expected keys and fails the instrument, not the score, when it does not.

## 3. How a Host harness provider works

1. The provider spawns the configured binary in `root` with an argv built by a pure function from `(task, caps, providerSpec)`. For Claude Code that is `claude -p` with a structured output format, a turn cap and a permission mode set to what a headless write needs; the exact flag set must be re-read from `claude --help` at spec time, not from this note. For Antigravity it is `agy` with whatever non-interactive and structured-output flags exist; that is unmeasured here and is an open item.
2. **Aliases do not cross the seam.** On the research machine `agy` is a shell alias (`caffeinate -s agy --dangerously-skip-permissions`). A spawned process does not expand aliases. The provider config must therefore name an executable and an explicit argv, and the permission-bypass flag must be a stated, cohort-recorded part of the argv, not something inherited from a dotfile. An eval run whose agent permissions came from a shell alias is not reproducible by anyone else.
3. **Environment scrubbing.** The Host harness is spawned with an allowlisted env. In particular the endpoint key must never be present in a Host harness child's environment, because that child has a shell tool and its transcript is retained.
4. **Isolation from the Operator's own setup.** A Host harness reads user-level settings, memory files and hooks from the Operator's home. This repository's own `~/.claude/CLAUDE.md` pulls in `RTK.md`, and a global hook rewrites shell commands. Those enter the session and are a confound for a steering eval. The provider must either run with a clean config directory or record exactly what leaked as cohort data. #222 decision 17 already notes that hook activation inside a fresh Host harness home is undocumented; the canary in 4.1 is how it gets measured instead of assumed.
5. **Layout is provider-specific.** Claude Code discovers `CLAUDE.md`, not `AGENTS.md`; this repository bridges with a symlink. A minted root for Claude Code needs `CLAUDE.md` to be a symlink to `AGENTS.md`; for a Host harness that reads `AGENTS.md` natively it does not. So the provider spec carries `discovery: { instructionFiles, hookWiringFiles }`, and the pure minter consumes it. The _content_ of the instructions and the config is identical across providers; only wiring differs.
6. The raw stdout is parsed by a pure per-harness parser into normalised events. Anything the parser cannot place becomes an `error` event, not a dropped line.

## 4. What a Host harness gives that a bare endpoint cannot

Each item below is a specific mechanism on the path "Operator's `intent` reaches the page the Contributor's agent writes".

| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

The hook is a script that parses a host-shaped payload, spawns `mh`, and emits a host-shaped answer. Silence is its dominant failure mode (`assess-hook.test.ts` header). | Does not exist. The framework can _call_ the hook script itself with a payload it composes, and paste the result in, but then the framework, not the host, decided when the hook fires, with what payload, and in what channel. ### 4.1 Canaries: prove a mechanism ran, never assume it

Trap 10 (`docs/agents/verification.md`): a hook reported `wired` is not one that will run. Each Host harness provider ships a **canary case** run once per provider per cohort, not per trial: a root whose only difference is a hook that writes a sentinel file and a `CLAUDE.md` / `AGENTS.md` line that says to write a second sentinel. The record's `hooksRan` and `agentsMdDiscovered` are read from the sentinels. A provider that cannot pass its canary is `instrument-failed` for the whole cohort and the report says "not measured", never "intent inert". Without this, a Host harness whose hook silently did not fire would be graded as the steered arm failing to move the agent, which is the single most damaging false negative this eval can emit.

## 5. The bare-endpoint provider: how it simulates a write, and what that costs

Two modes, deliberately kept apart because they measure different things.

### 5.1 Mode A: single-shot (control and isolation mode)

- **Request assembly (pure).** System or first message: the instruction file text and a fixed preface; then the seed file or files the task refers to, inlined with their paths; then the task. The `mh` answer, if any, is placed per `delivery`.
- **Reply handling (pure).** The reply is required to be the complete new content of exactly one named file, in a fixed envelope the parser extracts. A reply that does not match the envelope is a graded outcome (`unparsed-reply`), not an instrument failure, because the model's failure to follow the envelope is model behaviour; it is flagged separately from "wrote no marker" so a report cannot pool the two.
- **Apply (impure, tiny).** The extracted content is written to the path inside `root`. The grader then runs unchanged.
- **Fidelity cost.** No hooks, no tools, no discovery, no decision to call `mh`, no "before the write" moment, one turn. The delivery channel is entirely the framework's. The agent is also told the file path and the shape of the answer, which a real agent has to work out. This mode cannot say anything about whether a Host harness would deliver the signal. It can say something about whether, _given_ the signal in a specified position, a model uses it.

### 5.2 Mode B: stand-in host (minimal tool loop)

- **Tools offered:** `read_file(path)`, `write_file(path, content)`, optionally `list_dir(path)` and `run_mh(args)` where `run_mh` executes the compiled `dist/` `mh` against `root` with an argument allowlist (`--query`, `--check`, `--assess` and their path arguments).
- **What it is, and is not.** It is a host: it owns a model, tools, a turn cap and a session. Under the CONTEXT definition of Host harness ("the agentic CLI that runs the agent and owns the model, the tools, the permissions and the session") it _qualifies_ except that it is not an agentic CLI anyone uses. It must not be called a Host harness in a report, because a reader would assume the findings transfer to Claude Code. Call it a **stand-in host**, state in the cohort row that it is one, and never pool its rows with a real Host harness. It is also close to the product boundary "Act as a host harness" (`docs/vision/product.md`): the product does not, and this is repository tooling, but the closeness is the reason it should be the smallest thing that works and should not grow features (no permissions UI, no memory, no planning).
- **Hook simulation.** A PreToolUse-shaped delivery is simulated by the loop: before applying a `write_file` it calls `mh --query` for that path (through the same pure-built argv the real hook script would use) and returns the answer to the model as the tool result, asking it to retry. That is a plausible but invented protocol; real Claude Code hooks do not necessarily behave like this. It is a delivery-channel arm (`tool-result`), reported as such.
- **Fidelity cost.** Better than Mode A on file-write timing and on agent choice of when to call `mh`; still no real hook framing, no real AGENTS.md positioning, tool schemas invented, short context. The model also has _less_ to do than in a real session, which raises a ceiling effect: the earlier retired ablation study's saturation finding (#222 Problem Statement: a frozen gate saturates and discriminates nothing) is the failure to expect here too.
- **Cost of building it.** Three impure files (transport, fs apply, loop driver) and about half a dozen pure files. It is the largest piece of this design by far, and it exists only to approximate something the Operator already has for free on a subscription. Recommend building Mode A first and only building Mode B if Mode A produces a result worth interrogating for file-write timing.

### 5.3 Delivery channels the endpoint provider offers (the controllable variable)

| `delivery`    | meaning                                                                                                                              | what it isolates                                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `none`        | Instructions and task only; no `mh` JSON.                                                                                            | The **prior**: how often the marker appears with no signal. This is the floor for the low-prior marker and the control for every other cell. |
| `system`      | `mh` answer appended to the system prompt, verbatim.                                                                                 | Whether the model uses a signal it must treat as authoritative. Upper bound on consumption.                                                  |
| `user-prefix` | `mh` answer prepended to the user message, verbatim.                                                                                 | Whether the model uses a signal it may treat as user-supplied.                                                                               |
| `tool-result` | Returned as the result of a `run_mh` call or simulated hook. Mode B only.                                                            | Closest to a real hook's position; still invented framing.                                                                                   |
| `paraphrased` | Not offered. The answer is verbatim or not at all; a paraphrase would be a third arm, hiding a wording effect inside the instrument. |

## 6. What each provider can and cannot measure, per failure rung

Rungs: **never emitted**, **not reached**, **unparsed**, **rejected as prompt injection**, **parsed but ignored**, **partially acted on**. ("Rung" here is the failure ladder the research round uses; none of these terms are in `CONTEXT.md` yet.)

| rung                                                                                                                | Host harness provider                                                                                     | bare endpoint, Mode A                                                                                                                                                                                                                                                    | bare endpoint, Mode B                                                                         | honest verdict for the endpoint                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Never emitted** (`mh` or the hook never produced the intent text)                                                 | Measurable end to end: the transcript shows a hook with no output.                                        | Not measurable. The framework calls `mh` itself, so "emitted" is true by construction.                                                                                                                                                                                   | Not measurable for hook emission; measurable for whether the _agent_ ran `mh` when offered.   | **Cannot.** This rung is already covered by the Conformance suite and the deterministic half's hook proof. Do not let an endpoint run claim it.                |
| **Not reached** (emitted, never entered the model's context: host dropped it, wrong stream, truncated, hook silent) | Measurable: compare hook output against the transcript's model-visible turns; canary proves the hook ran. | Cannot exist. Delivery is the framework's act.                                                                                                                                                                                                                           | Cannot exist for the simulated hook; can exist for agent-called `mh` (agent never called it). | **Cannot.** Anything it reports under this rung is the framework's own decision to deliver.                                                                    |
| **Unparsed** (in context but the model failed to extract the `intent` from the JSON or text)                        | Measurable but confounded with later rungs; needs the transcript to infer.                                | **Measurable, and the endpoint's best use.** The framework injects the verbatim `mh` JSON in a known position; the neutralised-versus-as-written contrast then isolates reading.                                                                                         | Measurable.                                                                                   | **Can**, with delivery channel as an explicit cohort variable.                                                                                                 |
| **Rejected as prompt injection** (model treats the hook text as untrusted data and declines to follow it)           | Measurable, and this is where it actually happens; depends on the host's wrapping.                        | Not representative. Whether a model rejects text depends on where the text sits and how the surrounding system prompt frames it. A bare `system` or `user-prefix` placement is the placement _least_ likely to be rejected, so the endpoint will under-report this rung. | Partially: a tool-result placement is closer, framing still invented.                         | **Indicative only, biased toward zero.** Report as "not measured" unless the cell is `tool-result` mode B and then as "lower bound on rejection plausibility". |
| **Parsed but ignored** (understood the intent, wrote what it would have written anyway)                             | Measurable: marker absent, intent visible in the transcript.                                              | **Measurable**, with the ceiling caveat: a short context makes ignoring less likely than in a long real session.                                                                                                                                                         | Measurable with the same caveat.                                                              | **Can**, as an optimistic bound. A null here is strong (even the easiest conditions fail); a positive here is weak evidence about a Host harness.              |
| **Partially acted on** (some intents honoured, some not; marker present for one criterion of several)               | Measurable via per-criterion deterministic markers.                                                       | **Measurable** if the case defines several markers.                                                                                                                                                                                                                      | Measurable.                                                                                   | **Can**, with the same ceiling caveat.                                                                                                                         |

Summary: the endpoint provider can serve as a **control** (`delivery: none`, giving the marker's prior, which every Host harness cell also needs to be interpreted) and as an **isolation instrument for the consumption rungs** (unparsed, parsed but ignored, partially acted on). It cannot measure the two **transport rungs** (never emitted, not reached) and measures **rejected as prompt injection** with a known bias. A report must therefore print, per cell, which rungs the provider could observe, derived by a pure function from the record's capabilities rather than written by hand, so that "no failure on rung X" is never printed for a rung the provider could not see.

An endpoint result is a statement about the _model_ and the _words_. A Host harness result is a statement about the _model, the words and the delivery_. When the two disagree, the difference is the delivery, which is the interesting finding; when they agree the endpoint has saved subscription budget. Agreement and disagreement are both only interpretable when the same model is behind both, so the cohort row's `modelConfigured`/`modelSelfReported` fields are not optional.

Cheap model confound: an endpoint is often a cheaper or different model than the Host harness's. A difference between a cheap endpoint and Claude Code is then uninterpretable. The first-class comparison is the **same model through both paths** (for example an Anthropic Messages endpoint against `claude -p`), and a spec should say that is the only comparison the framework will print side by side.

## 7. Configuration, secrets and the missing-key rule

### 7.1 `.env`

1. `.env` is already in `.gitignore` (line 2). A tracked `.env.example` lists the variable names with no values and is the documentation.
2. Variables, illustrative: `EVAL_ENDPOINT_URL`, `EVAL_ENDPOINT_KEY`, `EVAL_ENDPOINT_FORMAT` (`openai-chat` or `anthropic-messages`), `EVAL_ENDPOINT_MODEL`. Several endpoints are named by a prefix (`EVAL_ENDPOINT_<NAME>_URL`) so a run can address a matrix; decide the naming in the spec.
3. Precedence: process env over `.env` over nothing. The read is `env-file.impure.ts`; the parse is a pure function over a string. No dotenv package is admitted: tenet 7 says standard library first, and the defect (a mis-parsed value) is loud because it becomes a failed auth or a missing key. If a spec agent prefers `process.loadEnvFile`, that is an engines-floor question and the answer must be checked against `package.json` before relying on it.
4. The endpoint transport uses global `fetch`. No OpenAI or Anthropic SDK: each is a dependency that would pass through the Admission bar, drags in transitive packages for two JSON shapes, and is exactly the sort of thing a hermetic gate does not want near it. Two hand-written wire formats is a small, loud surface.
5. Nothing reads `.env` at import time. Reading happens in the live entry point, and the result is passed down as an explicit record. The deterministic half never sees a real environment.

### 7.2 Keys are never logged

1. The key exists only as a field of a value passed to `endpoint-transport.impure.ts`, which adds it to the auth header (or `x-api-key`) as its last act. The pure request builder returns header _names_ and a body; it never holds the key.
2. Every string that crosses into a report, a transcript file or the console passes through a pure `redact(text, secrets)` first. The redactor masks every secret value, its URL-encoded and base64 forms, and obvious header lines; the `secrets` list is built from the config and not from guessing patterns. A unit test with a fake key proves a leaked occurrence is masked, which is what ARCH-003 permits (a hand-written value, not a mock).
3. Error text from `fetch` and from HTTP bodies is redacted before it becomes a `failure.message`. Some providers echo a key fragment in a 401 body.
4. The key is never put in argv (visible in process listings) and never put in a Host harness child's env (section 3, item 3).
5. Reports record `endpointHost` and a key _fingerprint_ at most (for example the last four characters, or none). Whether a fingerprint is acceptable is a decision for the spec.

### 7.3 Keys never in the gate

1. The eval Package's live entry point is a separate script (`npm run eval`) and is not referenced by `verify`, `verify:commit` or `ci.yml`. `verify` today is `archgate check && mh --check && eslint . && prettier --check . && tsc --noEmit && npm run lint:boundaries && npm run build && vitest run && knip`; the live script appears in none of those words.
2. **knip** is part of `verify` and will fail on an unreachable impure file. The live entry must be declared as an entry in the knip config so the impure files are reachable without being imported by anything the gate runs. That declaration is itself a seam to check, and trap 15's pattern applies: a guard that nothing reaches is green over nothing.
3. A structural test, in the deterministic half, over the repo's own files (a hand-read of `package.json` scripts and `.github/workflows/ci.yml`) asserts that no step in `verify`, `verify:commit` or the CI chain invokes the live script and that no file under `src/` outside the eval Package reads `process.env` for an `EVAL_` name. Per the "break what it guards" rule in the verification section, the test must be shown red against a deliberately wired copy before it is trusted.
4. The deterministic half's tests supply env records explicitly. No test reads `.env`, none calls `fetch`, and the pure files cannot import a builtin (ARCH-006), so the guarantee is the import graph, not discipline.
5. ARCH-001's Admission bar and tenet 7 mean no new runtime dependency is needed for any of this. If a spec agent disagrees, they must say which.

### 7.4 A missing or rejected key is an instrument failure, never a zero

1. **Preflight, before any trial.** A pure function takes the loaded env record and the provider list and returns, per provider, `ready` or `unconfigured` with the missing names (names only; never values). An unconfigured provider is reported as `not run: unconfigured` in the matrix and contributes no row to any score table. The process exits non-zero, per #222 decision 13: the instrument could not run.
2. **Per request.** A 401 or 403 is `auth-rejected`; a 429 after bounded retry is `rate-limited-exhausted`; a network error is `network`; a body that does not parse in the expected wire shape is `no-parseable-output`. All are `instrument-failed`. None enters the score table.
3. **Not instrument failures:** a model that returns an empty reply, refuses the task on policy grounds, writes no file, or hits the turn cap with nothing written. Those are graded outcomes and they tabulate (an empty reply scored as "marker absent" is correct, because the model really did produce nothing). The one boundary that needs a rule, not a guess: a turn cap hit mid-loop is graded; a wall-clock timeout is instrument. Spec agents should confirm.
4. **Partial failure inside a matrix.** If one cell of a matrix hits an instrument failure after other cells ran, the run keeps the finished cells, marks the failed cell `not run`, and the report's headline says "incomplete" rather than computing a rate over the cells that happened to work.
5. The classifier turning `(exit code, signal, status, stderr text, parse result)` into `ran` or an instrument failure kind is a pure function with a hand-written case for each kind, including the case trap 15 warns about: a failure kind that no provider can currently produce still needs an explicit decision, not a silent fallthrough to `ran`.

## 8. How the framework uses the record (so that the seam stays one seam)

1. The grader is one pure function over `(root contents, marker spec)`. It does not know which provider produced the root.
2. The arm-pair classifier (#222's `working`, `inert`, `wording`) is a pure function over graded records that refuses to compare records whose cohort rows differ in `providerKind`, `delivery` or `mode`.
3. The report tabulates rung coverage from capabilities (section 6), so a Host harness cell and an endpoint cell sit in the same table with different observed rungs.
4. Adding a third provider is a new `ProviderSpec` plus its argv builder and output parser, both pure, plus at most one impure file if its transport is neither a process nor an HTTP call. #222 "Out of scope" already anticipates exactly this plug-in point for a second Host harness; this design generalises it to a second kind.

## 9. Unverified or unmeasured here

1. Whether `agy` has a non-interactive structured-output mode, a hook facility, and `AGENTS.md` discovery. None was measured. The capability fields in the record exist so the answer can be measured by canary rather than assumed.
2. The exact `claude -p` flag set for a clean config directory and for stream-JSON output. Re-read `claude --help` when specifying; do not trust this note.
3. Whether a cheap endpoint model's baseline prior for the marker is low enough for the marker to count as a "low-prior" marker at all. This is a per-provider calibration that the `delivery: none` control exists to run, and it cannot be assumed to transfer from one model to another.
4. Whether `util.parseEnv` or `process.loadEnvFile` is available at this repository's Node engines floor.
5. Whether real endpoints echo key fragments in error bodies (some do; not measured for the specific services).

## What the spec agents must decide

1. **Whether a bare-endpoint provider is in scope at all, and under what wording of the boundary.** `docs/vision/architecture.md` says the product does not "run a model or hold an API key", and #222 user story 13 and decision 16 read as if the repository's tooling holds none either. A `.env` key held by the live eval script is a different claim. The spec must either amend #222's wording (repository tooling may hold an Operator-supplied key for an evaluation-only script that never ships) or restrict the endpoint provider to a documented, opt-in extra. It is a vision-level change if the Boundaries row is touched, and per `docs/vision/architecture.md` a "no" to question 4 of "Deriving a decision" is a stop.
2. **Mode A only, or Mode A and Mode B.** The recommendation is Mode A first, because it is the control and consumption-isolation instrument at a fraction of Mode B's cost. The spec must state what result would justify building Mode B.
3. **The `delivery` arms the endpoint provider offers** (`none`, `system`, `user-prefix`, and whether `tool-result` exists) and which one is the default for the control.
4. **Whether `delivery` and `mode` are cohort fields that block pooling.** Recommendation: yes; the arm-pair classifier refuses to compare across them.
5. **The failure-kind taxonomy and the one boundary case:** is a turn-cap hit graded and a wall-clock timeout an instrument failure, as proposed? What is the retry policy for 429 and for transient network errors, and is it counted in the record?
6. **The canary design.** Which sentinel, which case, how often (per cohort or per run), and what a failed canary does to the matrix. Also whether a canary failure on `agy` is expected (unmeasured) and should therefore be reported as "provider unsupported for this suite" instead of an exit-non-zero error.
7. **Isolation of the Host harness from the Operator's home** (clean config directory, scrubbed env, recording what leaked) and what is the cohort field if full isolation is impossible.
8. **Provider config schema.** What `ProviderSpec` looks like, where it lives (a committed non-secret file plus `.env` for secrets is the obvious split), how a matrix is named, and how `discovery` (CLAUDE.md symlink versus AGENTS.md) is declared so the minter stays pure.
9. **The same-model comparison rule.** Whether the framework refuses to print an endpoint cell beside a Host harness cell unless the configured model strings match, and how `modelSelfReported` is obtained for a Host harness.
10. **Redaction policy.** Fingerprint or none; whether transcripts are retained on disk at all, and for how long; what the gitignored report directory contains; whether a Host harness transcript, which may contain the Operator's own shell output, is stored.
11. **Package placement and classifiers.** Where the provider files live within the eval Package, whether the five impure files above can each carry exactly one ambient dependency, how the knip entry is declared so the live script is reachable and yet outside `verify`, and the structural test of 7.3.3.
12. **Glossary additions** for a later domain-modelling pass: provider, stand-in host, delivery channel, canary, rung (with the six rungs), capability record.
13. **The reporting rule for unobservable rungs.** The spec must make "this provider could not observe rung X" a printed, derived column, not prose, so a green row on an unobservable rung cannot appear.
