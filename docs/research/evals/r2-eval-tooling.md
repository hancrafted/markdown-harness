# R2 — Eval tooling for a steering-effectiveness eval

Question: can promptfoo, evalite or deepeval carry a level-one steering eval, where the subject under test is an agent session that leaves files behind, graded by regex over a marker word, across arms and repetitions, with nothing entering `npm run verify` or `ci.yml`? Level one means only: does the Operator's `intent` reach the agent and change what it writes.

Measured on 2026-10-07 on macOS, Node v26.5.0. Versions: promptfoo 0.124.0 (MIT, npm modified 2026-10-06), evalite 0.19.0 (npm `latest`; `1.0.0-beta.16` is the `beta` tag, last published 2026-02-20; MIT per the GitHub repo), deepeval 4.2.8 (Apache-2.0, PyPI 2026-10-02, Python `>=3.9,<4.0`). Where a claim comes from a probe I ran in a scratch directory under `/private/tmp/claude-501/`, it says "probed". Where it comes from a docs page, the URL is given. Where I could not confirm it, it says so.

## The shape of the problem

Every tool here was built around one call: `input -> model -> output text -> assertion over that text`. The subject here is different. A Host harness session (Claude Code, Antigravity) is driven headless in a minted root, runs for minutes, and its product is files on disk. The text it prints is incidental. So the same adapter job recurs in every tool: run the session, walk the minted root, and hand the file tree to the grader in whatever slot the tool calls "output". The tools differ in how much of the surrounding matrix, metadata and reporting they give back for free once that adapter exists.

Two further facts shape every comparison below.

- Each trial needs a fresh root, a seed, a cohort row and an arm-specific config. That is orchestration the tool does not know about. The cleanest split in all three cases is: the tool owns the matrix and the report, a small provider/task function owns the session.
- Grading here is one regex over one file. That is trivial. What the tools sell is mostly LLM-judged scoring, which this eval explicitly does not use. Their value is therefore the matrix, the repetition, the metadata and the output, not the assertion library.

## promptfoo

Sources: [custom provider docs](https://www.promptfoo.dev/docs/providers/custom-api/), [script provider docs](https://www.promptfoo.dev/docs/providers/custom-script/), [configuration reference](https://www.promptfoo.dev/docs/configuration/reference/), [telemetry](https://www.promptfoo.dev/docs/configuration/telemetry/), npm package metadata for 0.124.0.

**Driving a local CLI.** Two routes. The `exec:` provider runs any shell command with three positional arguments: the rendered prompt, a JSON string of provider options, and a JSON string of context carrying the test's vars and metadata. Probed: `exec:./a.sh` received three arguments and the context JSON included `vars` (with the injected `__repeatIndex`), `prompt` and `test`. The docs state stdout becomes `output` verbatim and is not parsed into structured fields, so an `exec:` script cannot set `metadata` or `tokenUsage`. The second route is a JavaScript or TypeScript provider (`file://provider.mjs`, class with `id()` and `callApi(prompt, context)`), which returns `{ output, error, metadata, tokenUsage, cost }`. For this job the JavaScript provider is the better route, because it can return `metadata` and `error` as fields. Working directory, environment and timeout behaviour of `exec:` are not documented on the page I read; I did not probe them.

**Matrix.** Providers x prompts x tests is native. Arms fit as either two providers (same script, different `config`, distinct `label`) or a `vars` value that selects the arm. Repetition is `evaluateOptions.repeat` (default 1). Probed: `repeat: 2` over two tests gave 4 results, and each carried `__repeatIndex`. `maxConcurrency` defaults to 4, which is wrong for sessions that spawn Host harnesses on a subscription; set it to 1 or low, and `delay` in milliseconds is available. Caching is on by default and must be disabled (`cache: false`), or a repeated identical trial returns the earlier result instead of running a session. This is a silent-wrong-answer trap specific to this job.

**Deterministic assertions over files.** Assertion types include `regex`, `contains`, `javascript`, `python`, with a `not-` prefix on most. Assertions run on the provider's `output`, not on disk. There are two ways to get a file tree in. (a) The provider reads the minted root after the session and returns the tree as JSON in `output`; a `javascript` assertion parses it and tests the target file. Probed and working. (b) A `javascript` assertion receives a context with the provider response and its `metadata`, so the assertion can instead read the root path from `context.providerResponse.metadata` and open the file itself. Both work; (a) keeps the result self-contained in the report, (b) keeps `output` small. A plain `regex` assertion then runs over the whole JSON blob unless a `transform` is used to select the one file's text first. Note that a `transform` on the assertion plus `regex` gives a declarative grader without custom code.

**Metadata and output.** A test's `metadata` is free-form. Probed: the output JSON carried `testCase.metadata`, the per-result `metadata` (merged test metadata plus provider `response.metadata`), `vars`, `latencyMs`, `tokenUsage`, `success`, `score`, and the `config` block. Run-level `metadata` exists too. Cohort fields that are static per run (mh version, Host harness version) can sit in top-level metadata; per-trial fields (arm, seed, model, turn count, duration) in provider `metadata`. Output formats: csv, txt, json, jsonl, yaml, html, xml and `junit.xml`. A `--output` path is repeatable.

**Does it stay out of the gate.** Not by default, but it can be made to. Telemetry is on by default and is disabled with `PROMPTFOO_DISABLE_TELEMETRY=1`; the update check against the npm registry is disabled with `PROMPTFOO_DISABLE_UPDATE=1`. The telemetry page says prompts, outputs and test cases are not sent. The sharing path is separate: the run banner prints a "Share" link and `promptfoo share` is an explicit command, so nothing is uploaded unless asked, but I did not find a documented master switch for it; I set `PROMPTFOO_DISABLE_SHARING=1` in the probe and cannot confirm from docs that the variable exists. Probed: a local run writes state to `~/.promptfoo/` (a `promptfoo.db` SQLite file, logs), which is outside the repo; `PROMPTFOO_CONFIG_DIR` relocated it. No server is needed for `eval`; `promptfoo view` starts one on demand. Nothing in the tool requires an account.

**Runtime, weight, licence.** MIT. Node `>=22.22` ok for this repo (`>=24`). It is a CLI you run with `npx promptfoo@0.124.0`; no need to add it to `package.json`. Its published package is 31.6 MB unpacked with 75 dependencies and a long optional-dependency list (cloud SDKs, `sharp`, `@openai/codex-sdk`, `@opencode-ai/sdk`). Probed: a cold `npx` run took about 38 s to fetch and start. As a dependency of this repo it would be the heaviest by far, and it would fall under architecture tenet 7 step 4 (transitive count, install scripts, licence). Used through `npx` outside `package.json` it never appears in `knip` or `dependency-cruiser` scope; that is the lighter path and needs a pinned version in a script.

**Agent-session handling.** There is no native notion of an agent session. The adapter is the JavaScript provider described above: mint root, spawn the Host harness headless, wait, walk the root, return the file tree as JSON in `output` and the cohort row in `metadata`. Notably, promptfoo documents built-in providers for coding-agent SDKs (the npm package lists `@openai/codex-sdk` and `@opencode-ai/sdk` as optional dependencies), which suggests agent-shaped providers exist; I did not read their docs and did not confirm Claude Code or Antigravity support, and they would be API-key or SDK paths rather than a subscription shell session, so I treat the custom provider as the route.

## evalite

Sources: [repository](https://github.com/mattpocock/evalite), [site](https://www.evalite.dev/), npm package metadata. Probed with 0.19.0 and vitest 4.1.11 in a scratch directory.

**Driving a local CLI.** An eval is `evalite("name", { data, task, scorers, trialCount, columns })` in an `*.eval.ts` file. `task(input)` is plain async TypeScript, so spawning a Host harness with `child_process` is just code. There is no provider abstraction and no `exec:`. Whatever `task` returns is `output`.

**Matrix.** `data` is the case list. There is no provider axis; arms and models are done by writing the loop yourself (generate `data` entries per arm, or call `evalite()` once per arm, or use variants, which exist in the exported schema as `variantName`/`variantGroup`). Probed: `trialCount: 2` produced two result rows per data entry, which is the repetition axis. Concurrency settings exist; I did not probe them. Because it runs inside a Vitest-style runner, `*.eval.ts` files are plain TypeScript with the repo's existing type setup.

**Deterministic assertions over files.** Scorers are functions `({ input, output, expected }) => number 0..1`, built with `createScorer`. Because `task` is arbitrary code, it can walk the root and return the file text (or a JSON tree) as `output`, and the scorer is a one-line regex. Probed and working. Scorers are TypeScript, so the regex lives in code rather than config.

**Metadata and output.** Per-result `columns` render arbitrary labelled values in the table and the stored result; probed: a column showing the arm appeared in the CLI table. The stored result carries `input`, `output`, `expected`, `duration`, `status`, scores, `renderedColumns`. I found no first-class per-run metadata or tag object in the exported shape; cohort fields would go into columns or into the `output` object. `evalite run --outputPath out.json` writes a JSON export (probed: top level `run` and `evals`). The site also advertises a static HTML export for CI, which I did not probe. State is a SQLite file under `node_modules/.evalite` (probed: `cache.sqlite`, `files/`), not the repo tree proper.

**Does it stay out of the gate.** I found no telemetry, PostHog or cloud strings in the installed package's `dist`, and no account concept; it is local-first with a local UI server for `evalite watch`. Probed behaviour to flag: `evalite run --help` documents `--threshold` as "fails process if score below threshold, default 100", yet a run scoring 50% exited 0 both with and without `--threshold 0`. Whatever the mechanism, I could not make exit status reflect score by default; this happens to suit the spec's rule that graded failures exit zero and only an instrument failure is non-zero, but the instrument-failure path (a `task` that throws) was not probed.

**Runtime, weight, licence.** TypeScript and Node, so it fits this repo's runtime and `tsc`. It depends on `@vitest/runner` and `@vitest/utils` `^4.0.x`, matching this repo's `vitest ~4.1.11`, but it also needs `better-sqlite3`, a native module. Probed: `npm i evalite@0.19.0` failed on this machine on `better-sqlite3@11` (`node-gyp rebuild` after `prebuild-install` found no binary for Node 26); an override to `better-sqlite3@13.0.3` installed cleanly (147 packages, 89 MB `node_modules` including vitest). That is an install-script and native-build dependency under tenet 7 step 4, and it is on the repo's Node range edge (`>=26`). The project is v0 with a v1 beta on a separate docs site (v1.evalite.dev), so the API I probed may change. MIT.

**Agent-session handling.** `task` is the adapter: mint root, spawn session, return the file text. This is the most natural fit of the three because nothing needs wrapping. The cost is that the matrix, arm handling, metadata and the exit contract are code the spec agents own.

## deepeval

Sources: [test cases](https://deepeval.com/docs/evaluation-test-cases), [data privacy](https://deepeval.com/docs/data-privacy), [environment variables](https://deepeval.com/docs/environment-variables), PyPI metadata for 4.2.8. Not probed; deepeval was not installed.

**Driving a local CLI.** deepeval is a Python library. A test is an `LLMTestCase` with `input`, `actual_output` and optional fields (`expected_output`, `context`, `retrieval_context`, `tools_called`, `name`, `tags`, `token_cost`, `completion_time`). You call your system yourself, put the result in `actual_output`, then run metrics via `evaluate(test_cases=[...], metrics=[...])` or a pytest-style `assert_test(test_case, [metric])` under `deepeval test run`. "Custom model" in deepeval means a judge model for LLM-judged metrics, not the subject under test. The subject is whatever Python you write: `subprocess.run([...])`.

**Matrix.** Parametrisation is pytest's (`pytest.mark.parametrize`), and `pytest-repeat`, `pytest-rerunfailures` and `pytest-xdist` are hard dependencies of the package. There is no provider axis. Hyperparameters can be logged with `@deepeval.log_hyperparameters`. Test cases can be marked `flaky`.

**Deterministic assertions over files.** The built-in metrics are overwhelmingly LLM-judged (G-Eval, answer relevancy, faithfulness, and so on). Per the docs page I read, `evaluate()` also supports an `expectations` mechanism that needs at least one `must`/`must_not` condition when no metrics are given; I did not read what those conditions are, and the page says they run locally. A deterministic regex grader means writing a custom `BaseMetric` subclass (`measure`, `is_successful`); the test-cases page does not document how, and I did not read the metrics docs. The file tree enters as the string `actual_output` (or in `tools_called` / `retrieval_context` entries), so the same JSON-blob adapter applies.

**Metadata and output.** `LLMTestCase` has `name`, `tags` and hyperparameters; the docs page I read did not mention a free-form metadata field. Results go to the terminal, to a local cache, and, if logged in, to Confident AI. I did not find an offline JSON/CSV export in the pages read; do not assume one.

**Does it stay out of the gate.** Telemetry is on by default through PostHog (event names, metric names, an anonymous UUID, public IP for regional analytics; results not stored). Opt out with `DEEPEVAL_TELEMETRY_OPT_OUT=1`. The docs I fetched do not say whether import or `evaluate()` makes network calls beyond that, and do not mention login prompts; a third-party search result recorded a past bug where opt-out broke evaluation (issue 1613, fixed in PR 1976), so opt-out is worth a smoke test on the pinned version. Update warnings are opt-in (`DEEPEVAL_UPDATE_WARNING_OPT_IN=1`). Confident AI is a separate hosted platform and is opt-in by login.

**Runtime, weight, licence.** Python `>=3.9,<4`, Apache-2.0, 31 declared requirements including `openai`, `grpcio`, `opentelemetry-*`, `posthog`, `pydantic`, `pytest` and plugins, `rich`, `typer`. This repo has no Python toolchain: `package.json` is Node-only, `vitest` is the runner, `dependency-cruiser`, `knip` and archgate all assume TypeScript. Adopting deepeval adds a second runtime, a virtualenv or `uv`/`pipx` step, a second lockfile, and a second language in a repo whose tenet 4 makes the portable contract the product, not the tooling. It also puts a runtime in the contributor path that no other part of the repo needs. Because the eval is outside the gate this need not break any rule, but it is the highest cost for the lowest gain, since the thing deepeval is best at (LLM-judged metrics) is exactly what this eval does not use.

**Agent-session handling.** Same adapter in Python: `subprocess` runs the session, the file tree is serialised to a string, a custom metric regexes it. deepeval's agentic features (`tools_called`, `ToolCorrectnessMetric`) score tool-use traces, not files left behind, so they do not apply here.

## The null option: a vitest-or-node runner with no framework

A Node script (or a `vitest` file with its own config, excluded from `verify`'s include glob) can do the whole job: loop over `cases x arms x seeds x trials`, mint a root, spawn the Host harness, read the file, test the marker with a regex, append one JSONL line carrying the cohort row, exit non-zero only if the instrument could not run. The repo already has this shape (the Conformance runners spawn `dist/`), the architecture tenet 7 order (standard library first, build when the code is small and a defect would be loud) points toward it, and a bug here is loud (a missing row, a crashed runner), not silent. No dependency, no telemetry surface, no hidden cache, no account.

What it loses, concretely: a results viewer and diff view across runs (promptfoo's `view`, evalite's UI); a parallelism/concurrency/retry scheduler (a few dozen lines, but they must be written and tested); built-in caching and its opposite, the guarantee that nothing is cached; an assertion vocabulary and `not-`/threshold/weight combinators; ready output formats (csv, html, junit); and, for the later levels, LLM-judge scorers and red-team generators, which this level does not need. It also loses a community's convention: someone reading the repo learns nothing by analogy. The honest trade is the matrix report: a JSONL file plus a small table printer replaces the viewer.

## What the spec agents must decide

1. **Framework or no framework.** The deciding question is whether the matrix report and viewer are worth a dependency under tenet 7. The grading itself (one regex over one file) needs none of the three tools. State the answer and the step of tenet 7's procedure that produced it.
2. **If a framework: where it lives.** `npx tool@pinned` in a script keeps it out of `package.json`, `knip` and `dependency-cruiser`; a `devDependency` brings it under both. promptfoo suits the first; evalite, being TypeScript with vitest peers, suits the second; deepeval needs a new toolchain either way.
3. **The adapter contract, whichever route.** Decide the shape the session returns: JSON tree in `output` (promptfoo, deepeval), file text (evalite), or a root path read later. Decide whether the regex lives in config (promptfoo `transform` + `regex`) or in code (evalite scorer, custom metric, runner).
4. **Where the cohort row lives.** Model, Host harness version, mh version, arm, seed must be per-trial. promptfoo and the null runner carry them natively; evalite has only `columns`; deepeval has `tags`. Decide whether the row is part of the tool's report or a separate sidecar file the runner always writes.
5. **Repetition and cache.** promptfoo's cache must be off for sessions. Decide what a "trial" is relative to a seed, and how the runner proves a trial actually ran a fresh session rather than replaying a cached one.
6. **Concurrency.** Subscription-driven sessions are rate-limited and may share a login. Decide the default concurrency (1 is the safe value) and who can raise it.
7. **Exit semantics.** Graded failures must exit zero and only an instrument failure non-zero. promptfoo exits non-zero on failed assertions by default (its docs I read do not state an override; confirm before relying on it); evalite exited 0 on a 50% score in the probe; the null runner decides for itself. Decide and prove it by breaking it.
8. **Keeping it out of the gate.** Name the exact mechanism: not in `verify`, not in `verify:commit`, not in `ci.yml` (verification trap 13), a distinct script name, and the telemetry/update/sharing switches set inside that script rather than in the Operator's shell. Decide whether a deterministic check proves the exclusion (for example a test that `verify`'s chain never names the eval script).
9. **Results location.** promptfoo and evalite keep state outside the minted root and the repo tree (`~/.promptfoo`, `node_modules/.evalite`); decide whether results are also written under a gitignored directory and whether the tool's own store is acceptable as the record.
10. **Node range.** The repo requires Node `>=24 <25 || >=26`. evalite's `better-sqlite3@11` did not install on Node 26 here; a spec that picks evalite must pin around that or accept the override.
11. **Version stability.** evalite has a `1.0.0-beta` line and a separate beta docs site; promptfoo ships frequently (0.124.0 as of 2026-10-06). Decide how a pinned version is recorded in the cohort row so that two runs are known comparable or not.

## Glossary gaps

Terms this research needed that `CONTEXT.md` does not define; I used them as plain English and did not coin synonyms. Issue 222 already lists several as pending for a domain-modelling pass.

- **arm** (steered vs intent-neutralised), and **trial** (one session of one case in one arm).
- **cohort row** (the per-trial metadata record).
- **marker word** (the low-prior token the grader looks for). `CONTEXT.md` already uses "marker" for the Conformance `<!-- expect: -->` marker, so a collision is likely; the term needs qualifying.
- **eval suite**, **eval case**, **intent carrier**, **intent address**, **rubric line** (all named in issue 222).
- **minted root** (a throwaway root made for one run) is used by the task statement and issue 222 but I did not find it as a defined term.
- **Steering content** (what `--query` returns) appears in issue 222 without a `CONTEXT.md` definition; the **Steering query** entry covers the asking, not the answer.
